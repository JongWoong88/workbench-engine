# decisions.md 형식

이슈 하나에서 **사람이 정했어야 할 결정**을 agent가 어떻게 골랐는지와, 그에 대한 담당자 평가를 모으는 기록 파일의 형식이다. 단계 스킬(`groundwork`·`plan`)과 `orchestrate`가 결정을 쓰고, 담당자(또는 `evaluate-decisions`)가 평가를 쓰고, `wb decision-stats`가 읽어 지표를 낸다. 이 문서가 형식의 정본이다.

- 담당자가 읽는 목록이다. 항목이 많을수록 평가 부담이 커지고 중요한 결정이 묻힌다. **비즈니스 영향이 없는 선택은 올리지 않는다**([무엇을 결정으로 기록하는가](#무엇을-결정으로-기록하는가)).
- **하네스**(agent harness)는 모델 바깥에서 agent의 동작을 정하는 것 전체다: 스킬·agent 정의·규칙 문서·워크플로(`board.yml`)·이슈 스키마·`bin/` 도구. 담당자 평가는 하네스를 고치는 근거가 되고, 하네스 버전별로 지표를 나눠 본다.
- groundwork의 결정 기록(ADR) 파일 `decision-<주제>.md`와는 별개다. ADR은 설계 결정 하나를 길게 쓰는 산출물이고, `decisions.md`는 담당자 평가를 받을 결정의 목록이다.
- `decisions.md`는 이슈 폴더(`records/{project}/{task_id}/`)에 하나만 둔다. 이슈가 없는 작업에는 만들지 않는다.

## 무엇을 결정으로 기록하는가

agent를 주니어 개발자, 담당자를 실무 책임자로 보면, **책임자가 "이건 물어봤어야지"라고 할 선택**만 기록한다. "이건 네가 정하고 문서에 근거만 남기면 돼"라고 할 선택은 기록하지 않고, 산출물 본문에 근거와 함께 쓴다.

기록한다 — 아래 중 하나에 영향이 있는 선택:

| 영향 | 예 |
|---|---|
| 사용자에게 보이는 동작 | 화면 흐름, 안내 문구, 응답·오류 형식, 사용자가 다시 입력해야 하는 것 |
| 고객·운영 데이터 | 저장값의 의미 변경, 데이터 일괄 정정, 운영 DB 조회·변경 요청 |
| 결제·계약·고지·약관 | 결제 상태, 보험료·보장, 고지 질문 |
| 다른 시스템·팀 | 다른 저장소(관리자 화면 등)가 읽는 값의 변화, 외부 기관·연동, 다른 팀과의 협의 |
| 업무 규칙·정책 | 규칙을 새로 정하거나 바꿈, 적용 대상(채널·사용자·기간 경계)을 정함 |
| 재발·잔여 위험 | 근본 원인을 이번에 고치지 않고 미룸, 증상만 막고 원천을 남김 |
| 릴리스 | 작업 기준 브랜치, 진행 중인 다른 브랜치와의 병합, 배포 순서·시점 |
| 요구사항 해석 | 원문 해석이 둘 이상이거나 요구사항끼리 상충함 |

기록하지 않는다 — 본문에 근거와 함께 쓴다:

- 조사 범위, 원인을 단정하는 정도, 문서 구성·서술 수준
- 구현·기술 설계 선택: 판정 위치, 메서드 시그니처·이름, 예외 메시지, 모델 복원 범위, 로그 형식
- 작업 분할, 테스트·검증 방식, 확인 결과를 남기는 위치
- 저장소·워크스페이스 규칙이나 기존 코드 관례를 그대로 따른 것(예: 지정 테스트만 실행, 같은 클래스의 기존 로그 방식)
- 진행 판단: 다음 단계로 넘길 범위, 단계를 건너뛰는 것
- 하나밖에 없는 방법

기록할지 망설여지면 위 "기록한다" 표의 어느 행에 해당하는지 적어 본다. 행을 고를 수 없으면 기록하지 않는다.

## 만들기

처음 결정을 기록하는 스킬이 한 번 만든다. 이미 있으면 만들지 않는다.

1. `wb new-record --to <task_id> --name decisions.md --title "<이슈 제목> 결정 기록" --repos -`
2. `wb link-output --task <task_id> --kind 결정 --path <decisions.md 경로> --desc "agent 결정과 담당자 평가"`
3. 그 스킬의 커밋 대상(`wb sync commit --files`)에 `decisions.md`와 이슈 파일을 넣는다. 링크 없이 커밋하면 `REC-UNLINKED`로 거부된다.

기존 `decisions.md`를 고치는 스킬은 `wb sync begin --files`와 `wb sync commit --files`에 이 파일을 넣는다.

```markdown
| D-2 | proposal | 환불 안내 메일 문구를 누가 정하는가 | | 상 | 누락 | 1fb6b38 |
| D-3 | design | 환불 상태를 정산 배치가 읽는 값으로도 내보내는가 | 내보낸다 | 중 | 승인 | 1fb6b38 |

## 상세

### D-1 환불 가능 기간에 결제 당일을 포함하는가

- 영향: 업무 규칙·정책
- 기각한 대안: 포함하지 않는다 — 요구 원문이 "결제 후 7일"만 말한다
- 근거: 기존 결제 취소 화면이 당일을 포함한다

## 반영 기록

| D | 원인 | 반영 |
|---|---|---|
| D-1 | 맥락 | `a1b2c3d` groundwork 제안 지침에 약관 문서 확인 추가 |
| D-2 | 일회성 | 반영하지 않음 — 외부 협의라 이번 요구에만 해당 |

## 산출물 지적

- design-refund.md 3장: 부분 환불 건을 대상에서 빼야 한다(결정이 아니라 설계 결함)
```

### 머리 두 줄

H1 바로 아래, 본문 첫 두 줄이다. 다른 줄을 끼우지 않는다.

| 줄 | 값 | 쓰는 주체 |
|---|---|---|
| `평가 상태:` | `평가 전` 또는 `평가 완료 (YYYY-MM-DD, 평가자)` | 만들 때 `평가 전`. 모든 항목의 평가가 끝나면 평가자가 `평가 완료`로 바꾼다. `orchestrate`가 재작성하면서 평가 빈칸 항목을 새로 만들면 `평가 전`으로 되돌린다 |
| `진행:` | 끝났거나 건너뛴 단계의 컬럼 id를 쉼표로, 컬럼 순서대로(`discovery`, `proposal`, `design`, `planning`). 없으면 빈 값. 건너뛴 단계도 넣어 재개 때 다시 하지 않게 한다 | `orchestrate`가 단계 스킬이 끝난 뒤 그 단계를 덧붙이고, 다음 컬럼 이동과 같은 커밋에 넣는다(`planning`은 단독 커밋). 단계 스킬은 고치지 않는다. 재개할 때 "끝난 단계"의 정본이다 |

- `평가 상태`가 `평가 전`이면 보드에서 읽는 사람이 이 기록을 확정 내용으로 오해하지 않는다.
- 담당자가 `수정` 평가로 단계를 다시 만들게 해도 `진행:` 줄은 되돌리지 않는다. 다시 만든 단계는 그 항목의 `다시 만든 단계`에 적는다.

### 요약 표

`## 요약` 아래 표 하나다. `wb decision-stats`는 이 표만 센다.

| 열 | 값 | 쓰는 주체 |
|---|---|---|
| `D` | `D-n`. 이슈 안 일련번호, 1부터. 지운 번호도 다시 쓰지 않는다 | 결정을 기록하는 스킬 |
| `단계` | 결정한 단계의 컬럼 id | 같음 |
| `결정할 것` | 질문 한 줄. "~하는가", "무엇으로 하는가" | 같음 |
| `채택안` | agent가 고른 안 한 줄. 누락 항목은 비운다 | 같음 |
| `영향도` | `상`·`중`([영향도 기준](#영향도-기준)). 담당자가 고치면 `중→상`처럼 원래 값과 바뀐 값을 남긴다 | agent가 쓰고 담당자가 고친다 |
| `평가` | [평가 값](#평가-값) 중 하나, 평가 전이면 빈칸 | 담당자 |
| `하네스` | 결정을 기록할 때 쓴 하네스(스킬·규칙·도구)의 설치 버전: `wb --version`(예: `1.2.0`). 엔진을 분리하기 전 기록은 workbench 커밋 7자리이고, 그대로 읽는다. 누락 항목은 같은 단계 다른 항목의 값, 없으면 `—` | 결정을 기록하는 스킬, 누락 항목은 평가자 |

- **결정 키**는 `단계` + `결정할 것`이다. 같은 단계를 다시 실행하거나 재개할 때, 같은 키의 항목이 있으면 새 번호를 쓰지 않고 그 항목을 고친다. 그래서 단계 스킬은 쓰기 전에 그 단계의 항목을 먼저 읽는다.
- 행은 `D` 번호 순으로 둔다. 영향도 순 정렬은 보고할 때 한다.
- 표 칸 안에 `|`를 쓰지 않는다. 코드 식별자(`플랜_선택` 같은 밑줄 포함 이름)는 백틱으로 감싼다. 마크다운 서식기가 밑줄을 강조 표시로 바꾸는 것을 막는다.

### 평가 값

| 값 | 뜻 | 지표 |
|---|---|---|
| `승인` | 담당자에게 올릴 결정이었고, 채택안이 맞다 | 결정 |
| `수정` | 채택안이 틀렸다. 상세 `평가:` 줄 `—` 뒤에 바뀐 내용을 쓴다. 올릴 필요가 없던 항목이라도 채택안이 틀렸으면 `수정`이다 | 결정 |
| `누락` | 담당자에게 올렸어야 할 결정인데 agent가 기록하지 않았다. 평가자가 새 `D-n`으로 추가한다 | 누락 |
| `제외(불필요)` | 올릴 필요가 없는 선택이었다(과잉 기록). 채택안이 맞는지는 따지지 않는다 | 과잉 |
| `제외(판정 불가)` | 실행 환경의 제약(로그·DB 접근 불가 등) 때문에 판정할 수 없다 | 집계에서 뺀다 |

- **누락은 결정에만 쓴다.** 산출물의 설계 결함·조사 누락처럼 "물어봤어야 할 결정"이 아닌 지적은 관련 항목이 있으면 그 항목의 `수정`으로, 없으면 `## 산출물 지적`에 적는다. 이 절은 집계하지 않는다.
- 지표 정의는 `bin/decision-stats.mjs` 머리 주석이 정본이다.

### 상세

`## 상세` 아래 항목마다 `### D-n <결정할 것>` 절을 둔다. 요약 표의 모든 `D-n`에 절이 있어야 하고, 절만 있고 표에 없는 번호가 있어서도 안 된다.

| 줄 | 내용 | 쓰는 주체 |
|---|---|---|
| `영향:` | [무엇을 결정으로 기록하는가](#무엇을-결정으로-기록하는가) "기록한다" 표의 행 이름. 둘 이상이면 `·`로 | agent |
| `기각한 대안:` | 고르지 않은 안과 이유. 여럿이면 `;`로 나눈다 | agent |
| `근거:` | 채택 이유. 확인한 코드·문서가 있으면 링크 | agent |
| `되돌리기 비용:` | `상`·`중`·`하`와 무엇을 고쳐야 하는지 한 줄 | agent |
| `근거 산출물:` | 이 결정을 적용한 산출물 절의 상대 링크. 재작성할 범위를 정할 때 쓴다 | agent |
| `평가:` | `<평가 값> · <평가자> · <날짜>`. `수정`이면 `—` 뒤에 바꾼 내용, `누락`이면 무엇을 정했어야 했는지, `제외`면 이유 | 담당자 |
| `다시 만든 단계:` | `수정`·`누락`으로 다시 쓴 단계의 컬럼 id들. 없으면 줄을 두지 않는다 | 재작성한 스킬 |

산출물 본문에는 결정 내용을 다시 쓰지 않는다. 채택안을 적용하고, 그 자리에 `([D-2](decisions.md#d-2-…))`처럼 번호를 링크한다.

### 반영 기록

`## 반영 기록` 아래 표다. `수정`·`누락` 항목마다 한 행이다. `제외(불필요)`가 반복되는 유형도 행을 둘 수 있다(기록 기준을 고칠 근거).

| 열 | 값 |
|---|---|
| `D` | 대상 `D-n`(여럿이면 `D-3·D-5`) |
| `원인` | `스킬 지침`·`맥락`·`워크플로`·`이슈 스키마`·`일회성` |
| `반영` | 하네스를 고친 커밋 7자리와 한 줄 설명, `반영 예정 — <무엇을>`, 또는 `반영하지 않음 — <이유>` |

원인 분류의 뜻:

| 원인 | 뜻 | 고치는 곳(예) |
|---|---|---|
| 스킬 지침 | 스킬이 이 결정을 알아보거나 고르는 기준이 없었다 | `plugin/skills/**` |
| 맥락 | 판단에 필요한 지식을 찾지 못했다 | 위키·저장소 문서, 스킬의 참조 순서 |
| 워크플로 | 단계 구성이나 순서가 맞지 않았다 | `board/board.yml`, `orchestrate` |
| 이슈 스키마 | 이슈 필드로 표현할 수 없었다 | `bin/lib/board.mjs`, lint |
| 일회성 | 이 이슈에만 해당한다 | 고치지 않는다 |

### 산출물 지적

`## 산출물 지적` 아래 목록이다. 선택 절이며 집계하지 않는다. 결정이 아닌 품질 지적(설계 결함, 조사 누락, 계획 범위)을 산출물 위치와 함께 적는다. 재작성이 필요하면 `orchestrate`가 이 목록도 반영한다.

## 영향도 기준

둘 다 담당자 평가 대상이다. 확신이 없으면 `상`으로 쓴다.

| 영향도 | 기준 |
|---|---|
| 상 | 요구사항 해석이 갈리거나 상충한다 · 업무 규칙·정책을 정하거나 바꾼다 · 고객·운영 데이터를 바꾸거나 운영 DB 작업을 요청한다 · 결제·계약·고지에 닿는다 · 다른 시스템이 읽는 값이나 사용자에게 보이는 동작이 바뀐다 · 근본 원인을 남긴다 |
| 중 | 위에 해당하지 않는 "기록한다" 항목: 릴리스(기준 브랜치·병합 순서), 다른 팀과 협의할 대상·주체, 운영 절차(알림·모니터링 대상) |

- 2026-10-30 이전 기록의 `하`는 읽기만 한다. 새로 쓰지 않는다.
- 담당자는 평가하면서 영향도를 고칠 수 있다. 집계는 담당자 값(`→` 뒤)을 쓴다.
