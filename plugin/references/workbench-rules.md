# workbench 이용 규칙

workbench 플러그인의 모든 스킬이 먼저 읽는 공통 규칙이다. 보드·기록 파일의 형식 세부(필드, 상태 규칙, 링크 표, 설정, lint 규칙)의 정본은 [workbench-format.md](workbench-format.md)다. 문서 저장소(이슈·기록이 있는 clone)의 위치는 `wb --help`의 `문서:` 줄이다.

## 영역과 권한

| 영역 | 경로(문서 저장소 기준) | 내용 | 에이전트 권한 |
|---|---|---|---|
| 보드 | `board/` | 작업 이슈 `tasks/{task_id}.md`. 컬럼·뷰는 엔진이 정한다 | 조회만. 예외는 아래 |
| 기록 | `records/` | 조사·검토, 제안서, 설계 초안, 작업 계획 등 **특정 시점의 기록 문서** | 작성 허용 |
| 대응표 | `projects.tsv` | project ↔ task_id 키 ↔ 저장소. project 값과 키의 단일 출처 | 조회만 |

### 보드

1. **기본은 조회만**: 이슈를 읽어 작업 맥락을 파악할 수 있지만, `board/` 아래 파일은 스스로 고치지 않는다. 이슈 생성·삭제, 컬럼 이동, 보관, 속성 변경, `board.yml` 변경이 모두 여기에 든다.
2. **명시적 지시가 있을 때만 고친다**: 사용자가 지시한 범위 안에서 `new-task`·`update-task`·`archive-task` 스킬로 고친다.
   - **`orchestrate` 실행 지시는 그 이슈의 전진 이동 지시를 겸한다.** `update-task`의 "명시적 지시"와 별개 경로다. 범위는 그 이슈 하나의 컬럼 이동뿐이다. 다른 이슈, 속성 변경, 종료 컬럼 이동은 포함하지 않는다.
     - 컬럼은 `discovery` → `proposal` → `design` → `planning` 순서로 앞으로만 간다. 이슈 규모에 따라 쓰지 않는 단계는 건너뛰고, 그 단계의 컬럼은 거치지 않는다(예: `backlog` → `discovery` → `planning`). `planning`은 건너뛰지 않는다. 시작 컬럼이 `backlog`·`on-hold`이면 첫 이동은 쓰기로 한 첫 단계다.
     - 이동은 `update-task`와 같은 절차로 한다. `wb sync begin --files <이슈 파일> <decisions.md>` → `wb move-task` → `wb lint --files …` → `wb sync commit --files …`. 이동 하나가 커밋 하나다.
   - **child 이슈는 계획서가 담당자 평가에서 승인된 뒤 만든다.** 사용자 지시로 `new-task`가 만든다. 평가에서 계획이 바뀌면 child를 되돌려야 하기 때문이다.
3. **예외 — 산출물 링크(의무)**: 이슈와 관련된 기록 문서를 만들었으면 지시가 없어도 **반드시** 그 이슈의 `outputs`에 링크를 단다.
   - 대상 이슈는 `wb find-task <task_id | 제목>`으로 찾는다. 후보가 여럿이면(`ambiguous`) 사용자에게 묻고, 이슈가 없으면 새로 만들지 말고 알리기만 한다.
   - 링크는 `wb link-output --task <task_id> --kind <구분> --path <문서> --desc "<한 줄 설명>"`으로만 단다. 다른 필드·컬럼은 건드리지 않는다.
   - 단 뒤에는 어느 이슈에 어떤 링크를 넣었는지 사용자에게 보고한다.

### task_id와 브랜치

- task_id는 `{키}-{번호}`(예: `APP-460`)다. 번호는 **반드시** `wb next-task-id <project>`로 발급한다. 보드에 이슈를 만들 때는 발급과 파일 생성을 한 번에 하는 `wb new-task`를 쓴다(`new-task` 스킬).
- 브랜치명은 `{유형}/{task_id}`(예: `feature/APP-460`)로 task_id와 맞춘다. 유형은 `hotfix`, `feature`, `refact`, `improvement`, `research` 중 하나다.
- project 값과 키는 `projects.tsv`에서 찾는다. 표에 없는 저장소는 키를 임의로 만들지 말고 사용자에게 확인한다.

### 기록

1. 기록 문서는 서비스 저장소가 아니라 문서 저장소의 `records/`에 쓴다. 서비스 저장소의 문서에는 현재 상태를 설명하는 상시 문서만 둔다.
2. 위치: 이슈가 있으면 `records/{project}/{task_id}/`, 없으면 `records/{project}/`. 이슈 없이 두었으면 사용자에게 알린다.
3. 파일은 `wb new-record --to <task_id | project> --name <파일명> --title <제목> [--repos <저장소,…>]`로 만든다. 위치와 프론트매터(`lifecycle`, `task_id`, `repos`, `base`)를 스크립트가 채운다. 생성된 프론트매터는 고치지 않는다.
4. 저장소의 상시 문서에서 `records/`를 링크하지 않는다. 필요한 판단 근거는 상시 문서에 직접 쓴다.
5. 비밀 정보(키, 비밀번호, 인증서, 운영 설정 파일)는 두지 않는다. 문서 저장소를 읽을 수 있는 사람은 모두 본다.
6. 이슈가 끝나면(종료 컬럼) 그 폴더의 기록은 동결한다. `new-record`가 거부한다.
7. 개발 중 코드 밖에서 확인한 결과(재현 확인, QA 검증, 운영 데이터 조회 결과)는 이슈 기록으로 남기고 산출물(구분 `검증`)로 링크한다. MR 설명·커밋 메시지·대화에만 두지 않는다.

## 참조할 지식과 문서

위키, 공통 문서, 저장소 문서의 위치와 이름은 환경마다 다르다. 이 플러그인은 특정 위치를 가정하지 않는다. 맥락이 필요하면 아래 순서로 찾는다.

1. **이 환경이 정한 출처**: 세션에 주어진 지침(사용자·워크스페이스·저장소의 CLAUDE.md 등)이 지식 출처와 참조 순서(예: 위키 먼저, 공통 문서, 문서 포털)를 정했으면 그대로 따른다
2. **대상 저장소의 안내와 문서**: 정한 것이 없으면 대상 저장소의 안내(CLAUDE.md, README, 에이전트용 지침 폴더)를 읽고, 거기서 가리키는 문서나 저장소의 문서 폴더를 목차(index·README)부터 읽는다
3. **workbench 기록**: 같은 project의 `records/`에 있는 이전 조사·설계·계획
4. **코드**: 서술할 사실은 코드·설정·데이터로 확인한다. 위키·문서·기록은 쓰인 시점 이후 낡았을 수 있다

찾는 자료가 없으면 건너뛰고, 무엇이 없어서 코드와 기록만으로 판단했는지 보고와 문서의 한계에 적는다.

## 커밋·푸시

보드·기록을 바꾸는 스킬은 끝날 때 바꾼 파일을 기본 브랜치(공유 설정 `branch`, 기본 `main`)에 커밋하고 바로 push한다. 다른 사람의 로컬 보드에는 다음 fetch 때(기본 30초) 보인다.

1. 쓰기 전에 `wb sync begin [--files <고칠 기존 파일>]`을 부른다. HEAD가 기본 브랜치인지 확인하고 원격 변경을 받는다. 아직 없는 파일(새 이슈·새 기록)은 `--files`에 넣지 않는다.
2. 다 쓴 뒤 `wb sync commit --files <바꾼 파일 전부> --message "<메시지>"`를 부른다. 지정한 파일만 lint → fetch → commit → push 한다.
   - 메시지는 `{유형}: {요약} ({task_id})` 관례를 따른다. 유형은 `docs`(기록), `chore`(보드) 등. 에이전트가 커밋에 붙이는 공동 작성자 줄이 있으면 메시지에 함께 넣는다.
3. sync가 거부하면 **멈추고 사용자에게 알린다**. 특히:
   - `SYNC-NOT-MAIN`: 문서 저장소 clone이 다른 브랜치에 있다. 브랜치를 바꾸지 않는다
   - `SYNC-DIRTY-TARGET`, `SYNC-STAGED-OTHER`, `SYNC-FF-BLOCKED`: 사람이 고친 내용이 있다. 그 편집을 덮어쓰거나 버리지 않는다
   - `SYNC-CONFLICT`, `SYNC-DIVERGED`: 원격과 충돌했다. `reset`·`rebase`·`stash`로 풀지 않는다
   - `SYNC-BUSY`: 같은 PC의 다른 작업이 문서 저장소 git을 오래 쓰고 있다. 잠시 뒤 같은 명령을 다시 실행하고, 계속되면 알린다. 잠금 파일을 직접 지우지 않는다
   - `SYNC-LINT`: 대상 파일의 규칙 위반이다. "누가"가 에이전트인 항목만 고쳐 다시 `sync commit` 한다
   - `SYNC-NO-TARGET`: `--files`의 경로가 어디에도 없다. 경로를 고쳐 다시 실행한다
   - `SYNC-ADD-FAILED`, `SYNC-INCOMPLETE`: 대상 파일이 커밋에 다 들어가지 못했다. `SYNC-INCOMPLETE`면 로컬에 커밋이 남아 있다. `reset`으로 되돌리지 말고 사용자에게 알린다
4. 문서 저장소를 worktree로 다루지 않는다. `git commit`·`git push`를 직접 부르지 않고 `wb sync`만 쓴다.
5. 스킬의 도구 사전 승인(`allowed-tools`)은 서브에이전트(검토 에이전트 등)를 부른 뒤에는 풀린다(2026-10-29 실측). 그 뒤의 수정·`wb` 실행에 승인 요청이 뜨거나 거부되면, 우회하지 말고 무엇을 하려는지 사용자에게 알리고 승인을 받는다. 승인되지 않으면 그때까지의 상태(만든 파일, 커밋 여부)를 보고하고 멈춘다.

## 도구 응답 규약

`wb <명령>`은 설치된 workbench 플러그인의 명령이다. **어느 폴더에서든 그대로 실행한다 — 문서 저장소 폴더로 `cd`하지 않는다.** 명령이 받는 경로는 문서 저장소 기준 상대경로(`board/tasks/…`, `records/…`)로 써도 된다. 문서 저장소의 파일을 읽을 때는 `wb --help`의 `문서:` 경로를 붙인 절대경로를 쓴다. `문서:`가 정해지지 않았으면 명령이 `ENV-DATA-ROOT`로 거부한다 — 아래 [처음 구성](#처음-구성)대로 한다. 모든 명령은 같은 형식으로 답한다(`--json`이면 JSON).

| 종료 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 | 성공 | 출력의 `다음:`·`참고:` 줄을 따른다 |
| 1 | 거부 | `수정`대로 고치고 `확인` 명령으로 다시 실행한다 |
| 2 | 사용법 오류 | 인자를 고쳐 다시 실행한다 |
| 3 | 환경 오류 | `수정`대로 환경을 갖춘다(문서 저장소 위치 설정, 플러그인 갱신 등). 못 하면 사용자에게 알린다 |
| 70 | 내부 오류 | 스크립트 결함이다. 우회하지 말고 사용자에게 보고한다 |

거부 메시지의 `누가` 줄이 고칠 주체다: 에이전트 → 바로 고친다 / 보드 수정 → 지시받은 범위 안이면 고치고 아니면 보고한다 / 사용자 판단 → 고치지 말고 보고한다. 거부를 피하려고 파일을 직접 써서 우회하지 않는다. `--force`, `--no-verify`는 사용자가 명시적으로 결정했을 때만 쓴다.

## 보드 화면

사용자가 보드를 보여 달라고 하면 `wb board --open`을 실행한다. 에이전트 셸에서는 백그라운드로 뜨고 주소를 알린 뒤 바로 돌아온다. 이미 떠 있으면 새로 띄우지 않고 그 주소를 알린다. 끄라고 하면 `wb board --stop`. 보드는 원격 기본 브랜치를 보여 주므로 push 전 내용은 보이지 않는다 — 보여야 하면 `--worktree`를 붙인다.

## 처음 구성

`wb`가 `ENV-DATA-ROOT`로 거부하면, 사용자에게 문서 저장소 clone 경로를 아는지 묻는다. 알면 `wb config set data-root <경로>`, 문서 저장소가 아직 없거나 clone부터 해야 하면 `setup` 스킬로 구성한다.

## 경로가 다른 PC

서비스 저장소들이 문서 저장소의 상위 폴더에 있지 않으면, 사용자가 알려 준 경로로 `wb config set workspace-root <경로>`를 실행한다. 저장소 하나만 다른 곳에 있으면 `wb config set repo-path <논리 경로> <폴더>`다. `wb config get`으로 확인한다. 기록의 저장소 링크는 고치지 않는다(논리 경로로 쓴다).
