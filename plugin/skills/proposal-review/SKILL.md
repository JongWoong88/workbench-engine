요구사항·제안서·기획서 문서를 세 관점에서 독립적으로 검토하고 취합해 보고한다.

> $ARGUMENTS

# 목표

- **관점을 섞지 않는다**: 비즈니스·기술·UX는 서로 다른 질문이다. 한 관점의 결론이 다른 관점의 판단을 끌고 가지 않도록 관점마다 따로 에이전트를 띄우고, 취합할 때도 판정을 조정하지 않는다
- **할 수 있는 판단만 한다**: 검토자는 코드·설정·스키마·개발 문서만 보고 **데이터 행은 보지 못한다**. 초기 문서에는 판단에 필요한 데이터도 없다. 그래서 데이터가 있어야 하는 판단은 결론을 내지 않고 "어떤 근거로 결론을 낼 수 있는지"를 제안한다. 시장·전략·선호처럼 서비스 밖에 기준이 있는 판단은 하지 않는다
- **다음 행동으로 이어지게 한다**: 보고서만 보고 문서 보완, 데이터 조회 요청, 기술 선결 조건 처리를 시작할 수 있어야 한다

# 관점 구성

| 관점 | 질문 | 산출 | 지침 |
|---|---|---|---|
| 비즈니스 | 수익 개선·사업 성장에 기여할 수 있는가 | 정성 판정 + 근거 설계 | [reviewers/business.md](reviewers/business.md) |
| 기술 | 현재 시스템 위에서 구현·운영 비용과 위험을 감당할 수 있는가 | 1~5점 평가 + 즉시 보류 조건 | [reviewers/technical.md](reviewers/technical.md) |
| UX | 사용자 경험이 나아지는가, 사용자가 실제로 필요로 하는가 | 정성 판정 + 근거 설계 | [reviewers/ux.md](reviewers/ux.md) |

세 관점 모두 [reviewers/common.md](reviewers/common.md)의 공통 규칙(접근 범위, 근거, 판정 체계, 출력 형식)을 따른다.

이 스킬의 대상이 아닌 것:

| 요청 | 담당 |
|---|---|
| 제안서·설계 문서를 **쓰는** 일 | `/workbench:groundwork` |
| 작업 계획 수립 | `/workbench:plan` |
| 코드 변경 리뷰 | `/code-review` |
| 저장소 현황 문서 작성 | `/workbench:documentation` |

# 워크플로우

### 0. 대상 파악

- 공통 규칙 [workbench-rules.md](${CLAUDE_PLUGIN_ROOT}/references/workbench-rules.md)를 먼저 읽는다
- **문서**를 읽는다. 인자로 경로가 없으면 사용자에게 묻는다. 요구사항·제안서·기획서가 아니면(작업 계획, 코드, 회고 등) 담당 스킬을 안내하고 멈춘다
- **대상 저장소**를 정한다: 문서에 적힌 서비스 → 문서가 놓인 `records/{project}/` → 둘 다 없으면 사용자에게 묻는다. `project`와 저장소 경로는 문서 저장소의 `projects.tsv`(`wb --help`의 `문서:` 경로)에서 찾는다. 여러 저장소에 걸치면 모두 적는다
- **이슈**를 찾는다: 인자의 `task_id` → 문서 frontmatter의 `task_id` → 문서가 `records/{project}/{task_id}/`에 있으면 그 폴더명. 찾은 task_id는 `wb find-task <task_id>`로 확인한다(`closed: true`면 기록이 동결되어 보고서를 그 폴더에 둘 수 없으니 사용자에게 묻는다). 없으면 이슈 없이 진행한다
- **주제**를 정한다: 파일명에 쓸 짧은 영문 kebab-case (`review-<주제>.md`)
- **기존 보고서**를 확인한다: 같은 문서에 대한 `review-<주제>*.md`가 있으면 덮어쓰지 않는다. 검토는 그 시점 문서에 대한 기록이므로 새 파일 `review-<주제>-<YYYYMMDD>.md`로 쓰고 이전 보고서를 링크한다

### 1. 컨텍스트 준비

- 서비스 컨텍스트는 메인이 모아 넘기지 않는다. 검토자가 각자 대상 저장소의 문서와 코드에서 직접 파악한다 ([공통 규칙 — 컨텍스트 파악](reviewers/common.md#컨텍스트-파악)). 메인이 요약해 넘기면 요약의 누락·왜곡이 세 관점에 똑같이 들어간다
- **기준 코드**를 기록한다: 저장소마다 `git rev-parse --abbrev-ref HEAD`, `git rev-parse --short HEAD`
- **출력 경로**를 정하고 폴더를 만든다 ([저장 위치](#저장-위치)). 관점별 결과는 `review-<주제>/` 폴더에 들어간다
- 이 단계에서 메인은 문서를 **해석하지 않는다**. 해석은 검토자 각자가 한다. 메인의 해석이 세 검토자에게 같은 전제로 들어가면 독립성이 깨진다

### 2. 세 관점 병렬 검토

**한 메시지에서** `Agent` 도구를 세 번 호출해 동시에 띄운다 (`subagent_type: general-purpose`). 프롬프트는 아래 [검토자 프롬프트](#검토자-프롬프트)를 채워 쓴다.

- 넘기는 것: 문서 경로, 저장소 경로, 공통 규칙과 **자기 관점** 지침 경로, 출력 파일 경로, 기준 코드, 사용자의 추가 프롬프트(있으면 원문 그대로)
- 넘기지 않는 것: 다른 관점의 지침·결과, 메인의 문서 해석이나 의견, "좋은 제안으로 보인다" 같은 기대

### 3. 취합

1. 세 결과 파일을 읽는다
2. **형식 점검**: [공통 규칙](reviewers/common.md#출력-파일)의 필수 섹션이 있는지, 판정마다 근거 경로가 있는지 확인한다. 빠졌으면 `SendMessage`로 그 검토자에게 한 번만 보완을 요청한다. 내용에 대한 반론이나 재판정 요청은 하지 않는다
3. **판정을 바꾸지 않는다**: 취합자는 관점 결과를 고치거나, 평균을 내거나, 한 관점으로 다른 관점을 반박하지 않는다. 세 관점을 합친 종합 점수나 "추진/보류" 단일 판정도 만들지 않는다
4. [취합 보고서 형식](#취합-보고서-형식)으로 `review-<주제>.md`를 쓴다
   - **교차 지점**: 같은 대상(코드 영역, 흐름 단계, 정책, 데이터)을 두 관점 이상이 짚었으면 나란히 놓는다. 어느 쪽이 맞는지 정하지 않는다
   - **요청 통합**: 세 관점의 문서 보완 요청과 데이터·자료 요청을 합치고 중복을 없앤다. 원래 번호(`BQ1`, `UE2` 등)를 남겨 출처를 추적할 수 있게 한다

### 4. 저장·링크·보고

- 프론트매터, 링크 형식, 이슈 산출물(`outputs`) 추가는 `/workbench:groundwork`의 [저장 위치](../groundwork/SKILL.md#저장-위치)·[작성 규칙](../groundwork/SKILL.md#작성-규칙)·[4단계](../groundwork/SKILL.md#4-산출물-링크와-보고)를 따른다. 산출물 구분은 `검토`다. 링크는 취합 보고서 하나만 건다
  - 파일을 만들기 전에 `wb sync begin`을 부른다. 거부되면 멈추고 알린다
  - 파일은 검토자를 띄우기 전에 `wb new-record`로 만든다: 취합 보고서 `--name review-<주제>.md`, 관점별 결과 `--name review-<주제>/{business,technical,ux}.md`. 검토자에게는 만들어진 파일을 `<OUT>`으로 넘기고 프론트매터·제목 아래에 쓰게 한다
  - 링크는 `wb link-output --kind 검토`로 달고, 마지막에 `wb lint --files <보고서 4개> <이슈 파일>`로 검사한다
  - `wb sync commit --files <보고서 4개> <이슈 파일> --message "docs: <보고서 제목> (<task_id>)"`로 커밋·push한다. 거부되면 멈추고 알린다
- 사용자에게 보고한다
  - 저장 경로 (취합 보고서, 관점별 결과 3개)
  - 관점별 결론 한 줄씩
  - 즉시 보류 조건·충돌 판정이 있으면 먼저
  - 문서 보완 요청 수, 데이터·자료 요청 수와 요청 대상
  - 형식 보완을 요청한 검토자가 있었으면 그 사실
  - 검토자가 발견한 문서-코드 불일치가 있으면 목록 (저장소 문서 갱신 대상 — `/workbench:documentation`)

# 저장 위치

| 경우 | 취합 보고서 | 관점별 결과 |
|---|---|---|
| 이슈 있음 | `records/{project}/{task_id}/review-<주제>.md` | `…/{task_id}/review-<주제>/{business,technical,ux}.md` |
| 이슈 없음 | `records/{project}/review-<주제>.md` | `…/{project}/review-<주제>/{business,technical,ux}.md` |

- 문서 저장소(이슈·기록이 있는 clone)의 위치는 `wb --help`의 `문서:` 줄이다. `wb`가 없으면(workbench 플러그인 미설치) 작성하지 말고 사용자에게 알린다
- 검토 대상 문서는 옮기거나 고치지 않는다

# 검토자 프롬프트

`<...>`를 채워 관점마다 하나씩 넘긴다. `<LENS>`는 `business` / `technical` / `ux`.

```
당신은 요구사항·제안서·기획서 문서를 검토하는 <관점명> 관점의 독립 검토자다. 다른 관점은 다른 검토자가 따로 맡는다.

- 검토 대상 문서: <DOC>
- 대상 저장소: <REPOS>  (기준 코드: <BASE>)
- 워크스페이스 루트: <WS>
- 공통 규칙: <SKILL_DIR>/reviewers/common.md
- 관점 지침: <SKILL_DIR>/reviewers/<LENS>.md
- 출력 파일: <OUT>  (이 파일에서 워크스페이스 루트까지의 상대경로 접두: <ROOT_REL>)
- 사용자 추가 요청: <원문 또는 "없음">

공통 규칙과 관점 지침을 먼저 읽고 그대로 따른다. 결과는 출력 파일에 쓰고, 최종 응답에는 결론 3~5줄과 출력 파일 경로만 남긴다.
```

- `<SKILL_DIR>`: 이 스킬의 기본 디렉터리 (스킬 로드 시 안내되는 Base directory)
- `<WS>`: 대상 저장소가 속한 워크스페이스 루트의 절대경로 (예: `<워크스페이스 루트>/<워크스페이스 폴더>` — 루트는 `wb config get`)
- `<ROOT_REL>`: 관점별 결과 파일에서 `<WS>`까지의 상대경로. 문서 저장소의 상위 폴더(워크스페이스 루트, `wb config get`)까지 이슈 있음 `../../../../../`, 이슈 없음 `../../../../`이고, 그 뒤에 워크스페이스 폴더를 붙인다 (예: `../../../../../ws/`)
