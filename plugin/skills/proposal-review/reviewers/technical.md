# 기술 관점

**질문:** 현재 시스템 위에서 이 제안을 구현하고 운영하는 비용과 위험을 감당할 수 있는가. 코드·설정·스키마·문서로 판단할 수 있는 관점이므로 **점수로 평가**한다.

**다루지 않는 것**
- 사업적 가치, 효과가 있을지 — 비즈니스 관점
- 사용자가 필요로 하는지, 경험이 나아지는지 — UX 관점

**판단하지 않는 것** (데이터나 조직 정보가 필요하다)
- 인일 단위 공수, 일정 — 상대 규모 등급(S/M/L)만 매긴다
- 인프라 비용 금액 — 새 리소스가 필요한지만 판단한다
- 트래픽에 따른 성능 정량 — 부하에 민감한 지점을 짚는 데서 멈춘다

## 1. 기준 코드

- 저장소별 기준 브랜치@커밋을 적는다
- 병행 브랜치(마이그레이션 브랜치, 미병합 대형 브랜치)가 있으면 어느 쪽을 기준으로 봤는지, 그 차이가 판정에 영향을 주는지 적는다 (확인 방법은 공통 규칙의 컨텍스트 파악)

## 2. 요구 분해

제안을 기술 요구로 쪼갠다. 문서가 명시하지 않았지만 구현하려면 반드시 필요한 것도 `[추론]`으로 넣는다 (예: 새 상태값이 생기면 상태 전이 배치·관리자 화면·연관 서비스의 처리).

| # | 요구 | 출처 | 닿는 영역 |
|---|---|---|---|
| TR1 | <…> | 문서 섹션 / [추론] | <흐름, API, 스키마, 배치, 알림, 외부 연동, 관리자 기능 등> |

## 3. 평가

항목마다 1~5점. 점수보다 **근거와 발견**이 중요하다 — 같은 3점이어도 무엇 때문인지가 다음 행동을 정한다.

| # | 항목 | 확인할 것 | 5 | 3 | 1 |
|---|---|---|---|---|---|
| T1 | 구현 가능성 | 현재 스택·아키텍처·외부 연동 방식으로 구현할 수 있는가. 외부 연동처(보험사·금융사·PG·제휴처 등)가 지원해야 하는 전제가 있는가 | 기존 패턴 재사용으로 가능 | 가능하나 새 패턴·외부 확인이 필요 | 핵심 전제가 현 구조나 외부 지원 범위 밖 |
| T2 | 기술적 명확성 | 데이터 정의, 예외 케이스, 상태 전이, 신청 유형별 분기, 비기능 요구(성능·정합성·가용성)가 정해져 있는가 | 바로 설계 착수 가능 | 모호점이 있으나 합리적 기본값이 있음 | 해석에 따라 구현이 크게 갈림 |
| T3 | 기술부채와의 관계 | 건드리는 영역이 알려진 결함·부채와 겹치는가. 우회 구현이 필요한가. 반대로 부채를 해소할 기회인가 | 부채 해소 또는 무관 | 부채 영역을 지나가나 악화시키지 않음 | 취약 영역 위에 우회 구현을 쌓음 |
| T4 | 변경 영향 범위 | 바뀌는 모듈·파일, 결합도, 스키마·데이터 마이그레이션, **다른 프로젝트**(같은 컬럼을 읽는 ETL, 관리자 시스템, 형제 서비스) 영향 | 격리된 변경 | 여러 계층이나 한 도메인 안 | 핵심 도메인 전반 + 마이그레이션 또는 타 프로젝트 파급 |
| T5 | 운영 부담 | 배치·외부 연동·알림 템플릿·모니터링 대상이 늘어나는가. 외부 변화에 취약한 구조인가. 과거 장애 유형이 재현될 구조인가 | 추가 운영 부담 거의 없음 | 관리 가능한 추가 부담 | 상시 대응이 필요한 구조 |
| T6 | 인프라 요건 | 새 리소스가 필요한가. 복제 지연(쓰기 직후 읽기), 세션·캐시, 파일 저장 같은 인프라 특성에 기대는가 | 기존 인프라로 충분 | 설정 추가 수준 | 새 인프라 도입 또는 인프라 특성과 충돌 |
| T7 | 보안·개인정보 | 개인정보·암호화 컬럼을 새로 다루는가. 인증·권한·조작 가능 식별자 같은 기존 취약점을 통해 노출 범위가 넓어지는가 | 영향 없음 | 통제 수단 추가로 해결 | 요건을 충족할 수 없는 구조 |
| T8 | 되돌림 가능성 | 플래그로 끌 수 있는가. 스키마·코드 체계·결제·계약 상태처럼 되돌릴 수 없는 변경이 있는가 | 언제든 끌 수 있음 | 되돌리려면 데이터 보정 필요 | 되돌릴 수 없음 |
| T9 | 검증 수단 | 기존 테스트 체계로 회귀를 잡을 수 있는가. 외부 연동을 대체할 수단이 있는가 | 기존 테스트로 검증 가능 | 테스트 추가로 검증 가능 | 운영에서만 확인 가능 |

## 4. 규모 등급

T4에서 찾은 변경 지점을 근거로 `S` / `M` / `L` 중 하나를 매긴다.

| 영역 | 변경 지점 | 신규 / 수정 | 근거 |
|---|---|---|---|
| <흐름·API·스키마·배치·템플릿·타 프로젝트> | <파일·모듈> | <…> | <경로> |

- S: 한 계층·몇 개 파일, 스키마 변경 없음
- M: 여러 계층 또는 스키마 추가(기존 데이터 무영향)
- L: 도메인 전반, 기존 데이터 마이그레이션, 타 프로젝트 동시 변경 중 하나 이상

## 5. 즉시 보류 조건

아래 중 하나라도 해당하면 점수와 관계없이 `즉시 보류 해당`으로 결론 맨 앞에 쓴다.

- 보안·개인정보 요건을 현재 구조로 충족할 수 없다
- 핵심 전제가 현재 연동 구조나 외부 지원 범위에서 불가능하다
- 되돌릴 수 없는 변경인데 검증 수단이 없다 (T8 1점 + T9 1점)
