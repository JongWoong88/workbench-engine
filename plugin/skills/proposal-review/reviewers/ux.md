# UX 관점

**질문:** 이 제안으로 사용자 경험이 나아지는가, 사용자가 실제로 필요로 하는 기능인가. 검토자는 사용자를 만나거나 사용 데이터를 볼 수 없으므로 두 가지를 답한다.

1. 현재 화면·흐름을 기준으로, 제안이 경험을 **구조적으로** 어떻게 바꾸는가 (정성 판정)
2. 사용자가 실제로 필요로 하는지 결론을 내려면 **어떤 근거를 어디서 찾아야 하는가** (근거 설계)

**다루지 않는 것**
- 매출·전환 효과 — 비즈니스 관점. 매출에 도움이 되더라도 사용자에게 불리하면(기만, 선택권 축소, 해지·환불을 어렵게 함) UX 관점에서는 `충돌`이다
- 구현 비용·기술 위험 — 기술 관점

**판단하지 않는 것** (서비스 안에 근거가 없다)
- 사용자의 선호, 니즈의 강도, 감성적 만족
- 시각 디자인 품질 — 소스로는 실제 렌더링을 볼 수 없다
- 접근성 실측

## 1. 사용자 문제 가설

| # | 누가 | 어떤 상황에서 | 무엇이 불편한가 | 지금은 어떻게 하는가 | 문서 근거 |
|---|---|---|---|---|---|
| UH1 | <스키마 조건으로 표현한 세그먼트> | <…> | <…> | <현재 경로·우회 방법> | <인용 또는 [추론]> |

- "누가"는 가능하면 스키마로 식별할 수 있는 조건으로 쓴다 (예: 채널, 상품 유형, 이용 목적, 신규·재이용 구분, 접속 지역, 대리 신청 여부). 식별할 수 없으면 그 사실을 적는다
- 문서가 사용자 문제를 말하지 않고 해결책(화면·기능)만 제시하면, 해결책에서 역으로 끌어낸 문제를 `[추론]`으로 적고 `UQ`로 문제 정의를 요청한다

## 2. 현재 상태 확인

제안이 전제한 "지금의 경험"이 실제와 맞는지 화면 템플릿, 화면 스크립트, 흐름 정의, 오류 메시지로 확인한다.

| 제안의 전제 | 실제 | 일치 | 근거 |
|---|---|---|---|
| <"현재 ~할 수 없다" 등 인용> | <확인한 현재 동작> | 일치 / 불일치 / 부분 | <경로:라인> |

- 전제가 틀렸으면 결론에 먼저 쓴다. 이미 해결된 문제이거나 다른 곳에 원인이 있을 수 있다
- 기기·앱 분기가 있으면 분기마다 확인한다

## 3. 정성 판정

| # | 항목 | 확인할 것 |
|---|---|---|
| U1 | 흐름 부담 | 단계 수, 입력 항목, 선택지, 팝업, 이동이 늘거나 줄어드는가. 되돌아가기·수정이 가능한가. 아래 변경 전후 표를 채운다 |
| U2 | 상태·결과 가시성 | 사용자가 지금 어디에 있는지, 무엇이 결정되었는지(금액·조건·기간 등), 다음에 무엇을 해야 하는지 알 수 있는가. 완료 후 안내(화면·알림 문구)와 이어지는가 |
| U3 | 오류 안내와 복구 | 차단·검증 실패 때 원인과 대처를 알려 주는가. 막다른 길(되돌아갈 수 없는 상태, 안내 없는 오류)이 생기는가 |
| U4 | 사용자 유형별 영향 | 서비스에 있는 사용자 유형 각각에서 — 예: 본인과 대리 신청, 신규와 재이용, 국내와 해외 접속, PC·모바일·앱 웹뷰, 가입·신청 후 조회·변경 이용자 — 깨지거나 어색해지지 않는가 |
| U5 | 일관성 | 기존 용어, 화면 패턴, 공통 컴포넌트, 형제 서비스의 같은 기능과 맞는가 |
| U6 | 통제권과 신뢰 | 사용자가 결과를 예측하고 되돌릴 수 있는가. 동의·결제·해지·환불 경로에 영향이 있는가. 기본값·문구가 사용자를 특정 선택으로 몰아가지 않는가 |
| U7 | 필요성 간접 신호 | 현재 우회 경로가 있는가(있으면 필요성은 낮아질 수 있다), FAQ·안내 문구·운영 이력에 관련 흔적이 있는가. **모두 `[간접]`으로 표시**하고 UE로 정량 확인을 연결한다 |

판정 표:

| # | 판정 | 발견 | 근거 | 풀리는 조건 (우려·충돌) |
|---|---|---|---|---|
| U1 | 부합 / 우려 / 충돌 / 판단 불가 | <…> | <경로> | <…> |

U1 변경 전후:

| 구분 | 현재 | 제안 후 | 근거 |
|---|---|---|---|
| 단계 | <n단계: …> | <…> | <흐름 정의 경로> |
| 입력 항목 | <…> | <…> | <템플릿 경로> |
| 분기·팝업 | <…> | <…> | <…> |

- 문서가 다루지 않아 해당 사항이 없는 항목은 "해당 없음"과 이유 한 줄

## 4. 근거 설계

UH마다 "사용자가 실제로 필요로 하는가"와 "경험이 나아졌는가"를 결론 내는 데 필요한 근거를 설계한다.

| # | 가설 | 알고 싶은 것 | 출처 | 조회 조건 / 수집 방법 | 가용성 | 지지 / 기각 조건 |
|---|---|---|---|---|---|---|
| UE1 | UH1 | <이탈 지점, 재시도, 실패 사유, 알림 반응 등> | `테이블.컬럼` (<경로>) 또는 외부 | <…> | 즉시 / 보정 / 신규 수집 / 외부 요청 | <비교 방식> |

- 서비스 DB 근거는 비즈니스 관점과 같은 규칙을 따른다: 스키마를 mapper·DAO에서 직접 확인, 제외 조건 명시, 한계(시간축 없음, 근사 등) 명시
- **외부 근거는 요청할 수 있게 구체적으로 쓴다**
  - 웹 분석: 페이지 경로·이벤트, 기간, 세그먼트(기기·유입), 보고 싶은 지표
  - 고객 문의: 기간, 분류·키워드, 보고 싶은 것(건수, 대표 사례)
  - 사용성 테스트·인터뷰: 대상 세그먼트, 과업 시나리오 2~3개, 관찰할 것
- 신규 수집이 필요하면 무엇을 어느 지점에서 기록해야 하는지 쓴다. 구현 방법은 쓰지 않는다
- 임계값은 정하지 않는다
