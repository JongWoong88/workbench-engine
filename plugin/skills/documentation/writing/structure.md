# 구조·흐름·데이터 모델을 쓸 때

시스템 구성, 계층, 처리 흐름, 데이터 모델, 설계 판단을 서술하는 섹션에 적용한다.

## 담을 것

- **다이어그램 하나 + 요약 문단.** 다이어그램이 말하지 않는 것만 글로 쓴다
- **구성요소의 책임과 금지 사항.** "무엇을 하는가"보다 "무엇을 하면 안 되는가"(허용되지 않는 의존, 우회 금지 경로)가 더 유용하다
- **흐름**은 "무엇을 왜"까지. 단계마다 진입점 코드 링크 하나면 충분하다
- **상태를 만드는 구조**는 생명주기 — 생성·갱신·만료·회수 시점 — 를 빠짐없이
- **데이터 모델**은 테이블의 역할, 관계, 데이터 수명, 그리고 코드로 보이지 않는 속성(암호화 대상, 보존 기간, 외부 스키마 소유권). 컬럼 전체 목록은 DDL·매퍼가 원본이면 링크한다
- 시스템 개요라면 **배포 구조**(환경, 인스턴스, 외부 경계)와 **품질 목표**(성능·가용성 수치)

## 설계 판단

되돌리기 어려운 선택에는 판단을 남긴다. 상시 문서에서는 결론을 겉면에, 근거를 `<details>`에 둔다.

- 결정 — 무엇을 택했는가
- 대안과 탈락 이유
- 결과 — 이 선택으로 얻은 것과 **감수한 것**

## 금지

- **메서드 호출 순서 옮겨 적기.** `validate()` → `confirm()` → `modify()` 식의 번호 목록은 코드 링크 하나로 대체한다
- 전체 클래스·엔드포인트·의존성 목록처럼 반드시 낡는 나열. 빌드 파일로 알 수 있는 기술 스택 버전
- 같은 데이터 목록(예: 암호화 대상 필드)을 여러 섹션·문서에 복제하기. 한 곳에 두고 링크한다
