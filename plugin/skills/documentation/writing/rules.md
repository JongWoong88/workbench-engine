# 업무 규칙을 쓸 때

정책, 가입·심사 조건, 상태 전이, 금액 계산처럼 **서비스가 지켜야 할 비즈니스 규칙**을 서술하는 섹션에 적용한다.

## 담을 것

- **조건 → 결과.** "A인 경우 B한다". 여러 조건이 얽히면 표로 쓴다 (조건 | 결과 | 근거)
- **경계와 예외.** 정상 흐름만 쓰면 구현자가 그 자리에서 판단하고, 그 판단이 사실상의 정책이 된다. 나이·기간·금액의 경계값이 포함인지 미만인지까지 적는다
- **이유 한 줄.** 왜 이 규칙인가. 길어지면 `<details>`로 접는다
- 규칙의 결과로 사용자에게 보이는 것 — 에러코드, 안내 문구, 차단 여부
- 판단 순서가 중요하면 우선순위를 번호로 밝힌다

## 형태별 요령

- **상태 전이**: mermaid `stateDiagram`. 전이마다 조건과 트리거를 적는다
- **계산 규칙**: 산식 + 반올림·절사 기준 + 통화 단위 + 적용 순서
- **시기별로 달라지는 규칙**: 변경 서사("5세대 전환 시 바뀐다") 대신 **기준별로 병기한 현재형 표**로 쓴다 (세대 | 규칙). 적용 기준(날짜, 버전, 코드)을 명시한다
- 다른 문서가 참조하는 규칙이면 번호를 붙인다. 삭제해도 번호를 재사용하지 않는다

## 금지

- **메서드 흐름을 따라 서술하기.** "1단계: `notContinuable()`, 2단계: `checkMBRenewed()`"처럼 쓰면 리팩터링에 문서 구조가 통째로 깨진다. 규칙 단위로 쓰고 구현 위치는 섹션 끝에 링크로 모은다
- 변경 경위와 배포 전략 — 기록 문서로
- 화면·API 설계 — 해당 섹션으로
