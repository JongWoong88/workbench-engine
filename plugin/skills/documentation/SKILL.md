아래 원칙에 따라 새로운 문서를 작성하거나 기존 문서를 수정한다.

> $ARGUMENTS

# 목표

- **포괄적 참조 가능성**: 비즈니스 규칙, 구조, 연동, 운영 등 프로젝트 핵심 정보가 문서화되어 에이전트가 활용 가능해야 함
- **Living Documentation**: 프로젝트에 변경이 발생하면 관련 문서에 즉시 반영되어야 함
- **Agent-Friendly Structure**: 헤더·표·다이어그램으로 구조화해 에이전트의 탐색 효율과 개발자의 가독성을 함께 확보

# 대원칙

문서 양식은 자유다. 대신 아래 여섯 가지는 **반드시** 지킨다. 3단계에서 독립 검토 에이전트가 이 원칙의 준수 여부를 검토한다.

1. **"지금 이렇다"만 쓴다.** 특정 시점의 내용(할 일, 진행 상황, 개선 권장, 알려진 이슈, 전환 계획, 현재 수치)은 저장소 문서에 쓰지 않는다. 그런 내용은 작업 공간의 기록 문서 몫이다 → [대상 문서](#대상-문서)
2. **사실마다 원본은 한 곳.** 같은 표·목록을 두 문서에 두지 않는다. 다른 문서에서는 한 줄 요약 + 원본 링크만 허용한다. 맥락을 위한 한두 문장의 언급은 중복이 아니다
3. **코드가 원본인 것은 쓰지 않는다.** 메서드 호출 순서, 시그니처, 파라미터 목록, 클래스 구조는 코드 링크로 대체한다. 문서는 코드에서 읽을 수 없는 것 — 업무 규칙과 그 이유, 외부 제약, 설계 판단의 근거, 운영 경험 — 을 쓴다
4. **주제 단위로 쓰고, 길어지면 하위 주제로 나눈다.** 한 문서 안에 규칙·구조·연동·운영이 함께 있어도 된다. 나누는 기준은 내용의 종류가 아니라 **400줄**과 **하위 주제**다. 새 문서를 만들기 전에 그 주제를 다루는 기존 문서가 있는지 먼저 찾는다
5. **겉면에는 결론을, `<details>`에는 상세를.** 접은 채로 읽어도 의미가 통해야 한다 → [계층적 노출](#계층적-노출-details)
6. **지켜야 할 것은 강도를 밝힌다.** 반드시(위반 불가) / 권장(이유 있으면 예외 가능) / 허용(선택) 세 단계만 쓴다. "가급적", "적절히", "~하는 것이 좋다"는 쓰지 않는다

# 워크플로우

### 0. 대상 파악

- **저장소 문서인가**를 먼저 확인한다. 애매하면 "6개월 뒤에도 이 문장이 참인가"로 판단한다. 요청이 검토서·제안서·조사 보고서·작업 계획처럼 특정 시점의 기록이면 이 스킬의 대상이 아니다. 작성하지 말고 `/workbench:groundwork`(조사·제안·설계) 또는 `/workbench:plan`(작업 계획)을 안내한다
- 대상 저장소와 [문서 루트](#파일-위치와-길이)를 정한다
- **주제**를 정하고 그 주제의 기존 문서를 찾는다
  - `Grep`으로 문서 루트에서 `^topics:` 와 주제어를 검색하고, 헤더(`^#{1,3} `)도 훑는다
  - 기존 문서가 있으면 **거기에 섹션을 추가·수정한다.** 새 문서는 기존 문서가 없거나 400줄을 넘길 때만 만든다

### 1. 컨텍스트 수집

- 대상 문서가 이미 있으면 전문을 읽는다
- 서술할 내용의 근거가 되는 코드·설정·데이터를 직접 읽어 **실제 구현과 일치**시킨다. 기존 문서만 믿지 않는다
- 쓸 내용에 해당하는 [서술 지침](#서술-지침)을 `Read`로 로드한다. 한 문서에 여러 내용이 있으면 여러 개를 로드한다
- 불확실하거나 추측이 필요한 내용이 있으면 **작성을 중단하고 사용자에게 확인**한다

### 2. 작성 / 수정

- 대원칙 + [작성 규칙](#작성-규칙) + 로드한 서술 지침을 적용한다
- 기존 문서 수정은 `Edit`으로 해당 섹션만 바꾼다. 전체 재작성은 사용자가 요청한 경우에만
- 수정하다 발견한 **기존 위반**(시점 내용, 중복 표, 낡은 서술)은 고치지 말고 목록으로 보고한다. 범위 밖 수정은 사용자가 정한다

### 3. 독립 검토

작성을 마치면 **작성에 관여하지 않은 검토 에이전트**를 병렬로 띄워 원칙 준수 여부를 검토받는다. 작성자는 자기 문장의 문제를 보기 어렵다.

1. [review-agents.md](review-agents.md)를 읽고, 아래 기준으로 검토자를 고른다

   | 작업 규모 | 띄울 검토자 |
   |---|---|
   | 새 문서, 또는 여러 섹션에 걸친 수정 | 수명 · 중복과 코드 재서술 · 사실 검증 · 형식 — **4개 모두** |
   | 섹션 1~2개 수정 | 사실 검증 · 수명 — 2개, 범위는 수정한 섹션 |

2. **한 메시지에서** `Agent` 도구를 여러 번 호출해 동시에 띄운다 (`subagent_type: general-purpose`)
   - 검토자에게는 파일 경로, 검토 범위, 원칙 파일 경로만 넘긴다. **작성 의도나 판단 근거는 넘기지 않는다** — 독립성이 검토의 가치다
3. 결과를 모아 지적마다 **채택 / 기각**을 판단한다. 기각은 사유를 한 줄로 남긴다
   - 채택 건 중 이번 작업 범위 안의 것은 고친다
   - 범위 밖(기존 섹션의 위반)은 고치지 않고 보고한다
   - 재검토는 돌리지 않는다. 사실 불일치를 고쳤으면 그 문장만 코드와 다시 대조한다
4. 사용자에게 보고한다: 검토자별 지적 수, 반영한 것, 기각한 것(사유), 범위 밖이라 남긴 것

# 대상 문서

이 스킬은 **각 저장소의 문서 루트에 포함되는 문서**만 작성·수정한다. 프로젝트와 비즈니스가 지금 어떻게 되어 있는지 설명하는 문서이며, 코드와 함께 계속 고친다.

| 구분 | 대상 | 예 |
|---|---|---|
| 작성·수정한다 | 저장소 [문서 루트](#파일-위치와-길이) 아래 문서 | 업무 규칙, 시스템 구조, 연동 규격, 운영 절차, 개발 규범 |
| 작성하지 않는다 | 작업 공간(`workbench/`) 아래 작업·기록 문서 | 조사·검토·제안서·설계 초안(`/workbench:groundwork`), 작업 계획(`/workbench:plan`) |

- **참조 방향**: 저장소 문서는 `workbench/` 아래 문서를 링크하지도, 근거로 인용하지도 않는다. 저장소 밖 문서는 저장소를 받은 사람에게 없다. 남겨야 할 판단 근거는 `<details>` 안에 직접 쓴다
- **흡수**: 작업 공간의 기록 문서는 입력으로 읽을 수 있다. 과제에서 확정된 내용(규칙, 구조, 계약, 운영 절차)을 저장소 문서로 옮길 때는 기록 문서를 읽되, 옮긴 내용은 저장소 문서만으로 이해되게 다시 쓴다. 옮길 후보(종료된 이슈의 기록과 대상 저장소의 문서 루트)는 `wb absorb-candidates [--task <task_id>]`로 뽑는다. 이 목록은 후보일 뿐이고, 이미 반영됐는지·무엇을 옮길지는 문서와 코드를 읽고 판단한다

# 작성 규칙

## 프론트매터

모든 문서는 YAML 프론트매터로 시작한다. 에이전트가 파일을 열지 않고도 수명과 주제를 알 수 있게 하기 위함이다.

```yaml
---
title: 결제와 환불         # 필수. 본문 H1과 동일
lifecycle: living          # 필수. 저장소 문서는 항상 living
topics: [결제, 환불, PG]   # 필수. 주제어. 기존 문서 탐색의 키
status: active             # 필수. draft | active | deprecated
updated: 2026-09-28        # 필수. 내용이 바뀐 날 (YYYY-MM-DD)
related:                   # 선택. 같은 저장소의 관련 문서 경로
  - <문서 루트>/data-model.md
---
```

- `topics`는 사람이 검색할 단어로 쓴다. 코드 식별자보다 업무 용어를 우선한다
- 프론트매터가 없는 기존 문서를 수정하면 **수정하는 김에 추가**한다

## 계층적 노출 (`<details>`)

| 항상 겉면에 | `<details>` 안으로 |
|---|---|
| 결론·결정·규칙 한 줄 요약 | 그에 이른 근거와 검토 이력 |
| mermaid 다이어그램 | 노드별 상세 설명 |
| 핵심 비교표, 규칙 목록 | 케이스별 예외 열거, 경계 조건 |
| 주요 필드 | 전체 필드 표, 긴 JSON·코드 예시 |
| 조치 절차 | 재현 로그, 스택트레이스 |

````markdown
### 티켓 저장

본인확인 결과는 Redis에 30분 TTL로 저장하고, 쿠키에는 티켓 ID만 싣는다.

<details>
<summary>Redis를 택한 이유 — DB 저장·JWT 자체 서명과의 비교</summary>

| 안 | 조회 비용 | 즉시 무효화 | 채택 |
|---|---|---|---|
| ... | | | |

</details>
````

- `<summary>`는 접힌 내용을 요약하는 문장으로 쓴다. "자세히 보기", "더보기" 금지
- 여는 `<details>` 다음 줄과 닫는 `</details>` 앞 줄은 비운다. 비우지 않으면 내부 Markdown이 렌더링되지 않는다
- `##` 헤더를 `<details>`로 감싸지 않는다. 중첩은 1단계까지, 5줄 미만은 접지 않는다
- 검색으로 도달하는 내용(에러 메시지, 에러코드, 장애 대응)은 접지 않는다. 접힌 내용은 브라우저 검색에 걸리지 않는다

## 링크와 구조

- 섹션은 `##`, `###`으로 나누고 헤더가 내용을 정확히 요약하게 한다
- 문서 링크는 저장소 루트 기준 경로와 앵커로: `[설명](/<문서 루트>/파일명.md#섹션-헤더)`
- 코드 링크는 경로와 라인으로: `[OrderService.java#L45-L80](/src/main/java/com/example/order/OrderService.java)`
- 키와 값을 구분하는 정보(속성, 필드, 규칙 비교)는 표로, 계층 구조는 목록으로
- 흐름·의존·상태는 mermaid로. 노드가 12개를 넘으면 나눈다. ASCII 다이어그램은 쓰지 않는다

## 파일 위치와 길이

- 문서는 프로젝트의 **기존 문서 루트**를 따른다: 저장소 안내(CLAUDE.md·README 등)가 정한 위치 → 이미 문서가 모여 있는 폴더(`docs`, `src/main/resources/docs` 등). 둘 다 없으면 어디에 둘지 사용자에게 묻는다
- 하위 디렉터리와 파일명은 기존 관례를 따른다. 관례가 없으면 주제명으로 짓는다 (`payment.md`, `domain/special-cases.md`)
- 문서 루트의 `index.md`(또는 `README.md`)에 주제별 목차를 유지한다. 문서를 추가·분할·삭제하면 목차도 같은 커밋에서 고친다
- 한 문서는 **400줄 이하**. `<details>` 안의 내용도 줄 수에 포함된다

## 변경 관리

- 작업으로 인한 문서 변경은 커밋 직전에 반영하고, 같은 커밋에 포함한다
- 업무 규칙이 바뀌는 작업이면 해당 규칙 서술을 **같은 커밋에서** 갱신한다. 구현과 문서가 어긋난 상태로 커밋하지 않는다
