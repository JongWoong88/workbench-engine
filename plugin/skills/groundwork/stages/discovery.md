# 조사·검토 문서를 쓸 때 (🔍 Discovery)

현황 조사, 요구사항 검토, 기술 검토, 장애 회고처럼 **특정 시점에 확인한 결과**를 남기는 문서에 적용한다.

## 공통

- **결론 먼저.** 발견과 권고를 3~7줄로 문서 맨 앞에
- **시점** — 조사 날짜를 절대 날짜로. 이슈가 끝난 뒤 다시 조사하면 고쳐 쓰지 않고 새 문서로 쓴다
- **범위와 방법** — 무엇을 어떻게 확인했는가. 범위 밖도 명시
- **발견** — 사실 → 검증 가능한 근거(코드 경로+라인, 로그 시각, 쿼리) → 영향
- **다른 곳이 읽는 값은 읽는 곳을 모두 찾는다** — DB 컬럼, API 응답, 메시지, 파일처럼 다른 코드가 읽는 값의 쓰기·의미를 다루면, 그 값을 읽는 곳을 대상 저장소 밖까지 찾는다. 범위는 워크스페이스의 모든 저장소다(`projects.tsv`의 저장소와 같은 워크스페이스 폴더의 저장소, 예: 서비스 저장소의 테이블을 관리자 저장소가 읽는다). 찾은 범위를 "범위와 방법"에 적고, 찾지 못한 범위(배치·BI 등 저장소 밖)는 한계에 적는다. 읽는 곳은 제안 단계에서 해법을 고르는 핵심 근거다
- **문서와 코드가 어긋난 곳은 발견으로 남긴다** — 조사 중 읽은 저장소 문서(설계·ERD·업무 규칙)가 코드와 다르면, 조사 종류와 관계없이 발견 하나로 적는다(문서 위치·문서 서술·코드 근거). 고치는 일은 계획에 넣는다
- **한계** — 확인하지 못한 영역, 추정에 의존한 부분. 추정에는 "추정"을 붙인다
- **권고** — "검토 필요"가 아니라 "X를 Y로 바꾼다"처럼 동작으로. 옵션이 여럿이면 비용·리스크·소요를 같은 축으로 비교

## 현황 조사

요구사항이 들어오기 전이나 직후에, 관련 영역이 **지금 어떻게 되어 있는지** 파악한다.

- 조사 질문을 먼저 적는다 — "무엇을 알기 위한 조사인가". 질문마다 답을 단다
- 저장소가 여럿이면 저장소별 차이를 같은 축의 표로 비교한다 (저장소 | 방식 | 근거 링크)
- 저장소 문서가 이미 설명하는 내용은 링크만 한다(어긋난 곳은 [공통](#공통)대로 발견으로)
- 해결책 설계로 넘어가지 않는다. 떠오른 방향은 권고에 한 줄로

## 요구사항 검토

주어진 요구사항을 현행 구현이 수용할 수 있는지 판정한다.

- 요구사항을 `R-1`, `R-2`로 번호 매기고 출처를 링크한다. 해석이 갈리면 채택한 해석을 적는다
- 현행 구현은 코드를 직접 확인하고 링크한다. 기존 문서가 낡았을 가능성도 검토 대상이다
- 요구사항마다 **네 값 중 하나로 단정**한다: `가능` / `조건부 가능` / `불가` / `요구사항 조정 필요`
- `조건부 가능`이면 선결 조건을 `P-1`로 번호 매겨 연결한다
- 기존 규칙·데이터·기능과의 **충돌 지점**을 따로 모은다
- 해결책 설계로 넘어가지 않는다. 대안이 보이면 한 줄만

## 기술 검토 (보안·안정성·성능 등)

특정 관점으로 구현을 점검하고 결함을 판정한다.

- 검토 기준을 먼저 적는다 — 무엇을 만족해야 "문제없음"인가. 기준마다 충족 / 부분 충족 / 미충족으로 판정한다
- 항목은 관점 접두사로 번호를 매긴다 (`S1` 보안, `A1` 안정성). 다른 문서가 항목 번호로 참조한다
- 항목마다: 현상 → 근거(코드 링크, 재현 조건) → 심각도(`High` / `Medium` / `Low`) → 영향 범위 → 조치안
- 조치가 진행되면 항목에 **판정 변경을 날짜와 함께 덧붙인다**("2026-09-15 조치 완료"). 원래 판정을 지우지 않는다
- 조치의 정본이 저장소 문서로 옮겨졌으면 그 문서를 링크하고, 조치 내용을 여기에 다시 쓰지 않는다

## 장애 회고

- 타임라인 — 탐지·대응·복구 시각
- 영향 — 시간, 범위, 사용자 체감
- 근본 원인 — 기여 요인까지
- 재발 방지 — 조치마다 담당자와 기한
- 사람이 아니라 시스템과 절차의 결함으로 서술한다
