착수 전 단계의 산출 문서를 작성하거나 수정한다.

> $ARGUMENTS

인자에 `--자율` 플래그가 있으면 **자율 모드**, 없으면 수동 모드다. 이슈가 있으면 두 모드 모두 결정을 `decisions.md`에 남긴다. 절차와 자율 모드에서 바뀌는 규칙은 [decision-recording.md](${CLAUDE_PLUGIN_ROOT}/references/decision-recording.md)를 따른다.

# 목표

- **판단의 근거를 남긴다**: 무엇을 확인했고, 무엇을 제안했고, 왜 그렇게 설계했는지를 그 시점의 코드 기준으로 남긴다
- **다음 단계의 입력이 된다**: 조사는 제안의, 제안은 설계의, 설계는 `/workbench:plan`의 입력이다. 앞 단계 문서를 읽으면 다음 단계를 시작할 수 있어야 한다
- **흡수하기 쉽게 쓴다**: 과제가 끝나면 확정된 내용은 `/workbench:documentation`이 저장소 문서로 옮긴다. 확정될 규칙·구조는 처음부터 저장소 문서의 서술 형식으로 쓴다

# 대상 문서

| 보드 단계 | 문서 | 파일명 (기본) | 단계 지침 |
|---|---|---|---|
| 🔍 Discovery | 현황 조사, 요구사항 검토, 기술 검토(보안·안정성 등), 장애 회고 | `discovery.md`, `review-<주제>.md` | [stages/discovery.md](stages/discovery.md) |
| 🤝 Proposal | 제안서, 방안 비교 | `proposal.md`, `proposal-<주제>.md` | [stages/proposal.md](stages/proposal.md) |
| 📐 Design | 정책·기술 설계 초안, 아키텍처 결정 기록 | `design-<주제>.md`, `decision-<주제>.md` | [stages/design.md](stages/design.md) |

- 단계는 이슈의 보드 컬럼이 아니라 **문서의 내용**으로 정한다. Design 컬럼의 이슈에서도 추가 조사 문서를 쓸 수 있다
- 파일명은 기본값이며 강제하지 않는다. 같은 종류가 여럿이면 주제를 붙인다

이 스킬의 대상이 아닌 것:

| 문서 | 담당 |
|---|---|
| 저장소에 포함되는 현황 문서(업무 규칙, 구조, 연동 규격, 운영 절차) | `/workbench:documentation` |
| 작업 계획(Sub-Task, 구현 순서) | `/workbench:plan` |

# 대원칙

아래 여섯 가지는 **반드시** 지킨다. 3단계에서 독립 검토 에이전트가 준수 여부를 검토한다.

1. **시점을 박는다.** 작성일은 절대 날짜로, 기준 코드는 프론트매터 `base`로 남긴다. "현재", "최근" 대신 날짜를 쓴다. 이슈가 진행 중인 동안에는 고쳐 쓸 수 있고, 이슈가 ✅ Done / 🗑️ Dropped가 되면 동결한다. 동결된 문서의 판단을 바꾸려면 새 문서를 쓰고 이전 문서를 링크한다
2. **근거로 말한다.** 사실 주장에는 확인 가능한 근거(코드 경로+라인, 로그 시각, 쿼리, 출처 문서)를 붙인다. 직접 확인하지 못한 것은 "추정"이라고 쓴다. 기존 문서만 믿지 않고 코드를 직접 읽는다
3. **결론이 먼저다.** 문서 맨 앞 3~7줄에 결론(발견·권고·결정 요청·채택안)을 둔다. 결론만 읽어도 다음 행동을 정할 수 있어야 한다
4. **원본은 한 곳.** 저장소 문서·코드에 있는 내용은 옮겨 적지 않고 링크한다. 앞 단계 기록의 표·수치도 복제하지 않고 인용 + 링크한다. 메서드 호출 순서, 시그니처, 클래스 구조를 서술하지 않는다
5. **결정할 수 있게 쓴다.** 권고는 "검토 필요"가 아니라 "X를 Y로 바꾼다"처럼 동작으로 쓴다. 선택지가 여럿이면 같은 축(비용·리스크·소요·되돌리기 쉬움)으로 비교한다. 미결 사항은 번호를 매겨 누가 결정해야 하는지 적는다. 자율 모드에서는 미결 사항을 두지 않고 안을 골라 `decisions.md`의 `D-n`으로 기록한다
6. **지켜야 할 것은 강도를 밝힌다.** 반드시 / 권장 / 허용 세 단계만 쓴다. "가급적", "적절히"는 쓰지 않는다

# 워크플로우

### 0. 대상 파악

- 공통 규칙 [workbench-rules.md](${CLAUDE_PLUGIN_ROOT}/references/workbench-rules.md)를 먼저 읽는다
- **이슈**를 찾는다: `wb find-task <task_id | 제목 일부>`. `status: ambiguous`면 사용자에게 묻고, 찾지 못하면 이슈 없이 진행한다고 알린다. 결과의 `closed: true`는 기록이 동결된 이슈다
- **단계**를 정한다: [대상 문서](#대상-문서) 표 기준. 작업 계획이나 저장소 현황 문서 요청이면 담당 스킬을 안내하고 멈춘다
- **기존 기록**을 확인한다: 이슈의 산출물 목록(`find-task` 출력의 `outputs`)과 이슈 폴더를 읽는다
  - 같은 주제의 문서가 있고 이슈가 진행 중이면 **그 문서를 수정한다**
  - 동결된 문서(이슈 종료)의 판단을 바꿔야 하면 새 문서를 쓰고 이전 문서를 링크한다

### 1. 컨텍스트 수집

- 앞 단계 산출물을 먼저 읽는다 (설계라면 조사·제안 문서, 제안이라면 조사 문서)
- 공통 규칙 [workbench-rules.md](${CLAUDE_PLUGIN_ROOT}/references/workbench-rules.md)의 "참조할 지식과 문서" 순서로 확인한다 — 이 환경이 정한 지식 출처(위키·공통 문서 등) → 대상 저장소의 안내·문서 → workbench 기록 → 코드. 없는 자료는 건너뛰고 한계에 적는다
- 서술할 사실은 코드·설정·데이터를 **직접** 읽어 확인한다
- 결론을 좌우하는 동작은 **누락 없이** 확인한다: `repos`의 모든 저장소, 예외·실패 경로, 상태값 전부. 검토자는 문서에 붙은 근거만 대조하고 누락은 의심만 보고하므로, 누락 확인은 작성자 몫이다
- 해당 [단계 지침](#대상-문서)을 `Read`로 로드한다. 설계 문서는 단계 지침이 가리키는 `/workbench:documentation`의 서술 지침도 함께 로드한다
- 요구사항 해석이 갈리거나 추측이 필요하면 **작성을 중단하고 사용자에게 확인**한다. 자율 모드에서는 최적안을 골라 `D-n`으로 기록하고 계속한다
- 이슈 폴더에 `decisions.md`가 있으면 이번 단계의 항목을 읽는다

### 2. 작성 / 수정

- 쓰기 전에 `wb sync begin [--files <고칠 기존 기록> <기존 decisions.md>]`을 부른다(새 파일은 넣지 않는다). 거부되면 멈추고 알린다 — 공통 규칙 "커밋·푸시"
- 결정을 내릴 때마다 `decisions.md`에 기록하고, 본문에는 채택안과 `D-n` 링크만 쓴다 — [decision-recording.md](${CLAUDE_PLUGIN_ROOT}/references/decision-recording.md) "쓰는 중"
- 대원칙 + 단계 지침 + [작성 규칙](#작성-규칙)을 적용한다
- **새 문서**는 파일을 직접 만들지 않고 `wb new-record --to <task_id | project> --name <파일명> --title <제목> [--repos <저장소,…>]`로 만든 뒤 본문을 쓴다. 저장소가 없는 project(`common` 등)이거나 근거 저장소가 없으면 `--repos -`. 위치·프론트매터(`repos`·`base`)는 스크립트가 채운다. 생성된 프론트매터는 고치지 않는다
- 기존 문서 수정은 `Edit`으로 해당 섹션만 바꾸고 `updated`를 갱신한다. 전체 재작성은 사용자가 요청한 경우에만
- 프론트매터가 없는 기존 기록을 고치면 `wb new-record … --print`로 받은 프론트매터를 맨 앞에 붙인다

### 3. 독립 검토

작성을 마치면 **작성에 관여하지 않은 검토 에이전트**를 띄워 검토받는다.

1. [review-agents.md](review-agents.md)를 읽고 검토자를 고른다

   | 작업 규모 | 띄울 검토자 | 범위 |
   |---|---|---|
   | 새 문서 | 사실 검증 · 형식 — 2개 | 전체 |
   | 여러 섹션에 걸친 수정 | 사실 검증 · 형식 — 2개 | 사실 검증: 이번에 바꾼 행·항목 / 형식: 수정한 섹션 |
   | 섹션 1~2개 수정 | 사실 검증 — 1개 | 이번에 바꾼 행·항목 |

   - 이슈가 있는 기록이고 "새 문서"나 "여러 섹션에 걸친 수정"이면 **결정 누락** 검토자를 하나 더 띄운다([decision-review.md](${CLAUDE_PLUGIN_ROOT}/references/decision-review.md)). 채택한 지적은 `decisions.md`에 `D-n`으로 추가한다
   - "이번에 바꾼 행·항목"은 섹션이 아니라 바뀐 문장·표 행·번호 항목(`C-3`, `K-2` 등) 단위로 적는다. 이미 검증받은 행은 넘기지 않는다. 작업 공간이 git이면 `git diff -- <문서>`로 바뀐 부분을 확인한다
2. **한 메시지에서** `Agent` 도구를 호출해 동시에 띄운다 (`subagent_type: general-purpose`, 사실 검증은 `model: sonnet`). 검토자에게는 파일 경로, 범위, 원칙 파일 경로만 넘기고 **작성 의도나 판단 근거는 넘기지 않는다**
3. 지적마다 **채택 / 기각**을 판단한다. 기각은 사유를 한 줄로 남긴다. `누락 의심`은 검토자가 확인하지 않은 것이므로 작성자가 직접 코드에서 확인한 뒤 판단한다. 범위 밖(기존 섹션의 문제)은 고치지 않고 보고한다. 재검토는 돌리지 않는다

### 4. 산출물 링크와 보고

- 이슈 폴더에 문서를 만들었으면 산출물 링크를 단다: `wb link-output --task <task_id> --kind <구분> --path <문서> --desc "<한 줄 설명>"`
  - 구분: `조사` · `검토` · `회고` · `제안` · `설계` · `결정` 중 하나
  - 경로 계산, 파일 확인, 중복 방지는 스크립트가 한다(이슈 프론트매터 `outputs`에 들어간다). 보드에서 허용된 수정은 이 산출물 추가뿐이다. 컬럼·속성·parent·보관은 건드리지 않는다
- `decisions.md`를 이번에 만들었으면 `wb link-output --task <task_id> --kind 결정 --path <decisions.md> --desc "agent 결정과 담당자 평가"`. 결정을 기록했으면 `wb decision-stats --task <task_id> --check`로 형식을 확인한다
- 마지막에 검사한다: `wb lint --files <만들거나 고친 기록> <decisions.md> <이슈 파일>`
- 커밋·push한다: `wb sync commit --files <만들거나 고친 기록> <decisions.md> <이슈 파일> --message "docs: <문서 제목> (<task_id>)"`. 이슈 없는 기록이면 `(<project>)`. 거부되면 멈추고 알린다
- 스크립트가 거부하면(종료 코드 1·2) 출력의 `수정`대로 고치고 `확인` 명령으로 다시 실행한다. `누가`가 "보드 수정"이나 "사용자 판단"이면 고치지 말고 보고에 넣는다. 파일을 직접 써서 우회하지 않는다 (응답 규약: [형식 규칙](${CLAUDE_PLUGIN_ROOT}/references/workbench-format.md) "도구")
- 사용자에게 보고한다: 저장 경로, 결론 요약, 검토자별 지적 수와 반영·기각(사유)·범위 밖 항목, 링크를 넣은 이슈(또는 이슈 없이 두었다는 사실), lint가 남긴 사용자 판단 항목, 이번에 추가·수정한 `D-n`(영향도 순)

# 저장 위치

착수 전 단계의 문서는 특정 시점의 **작업·기록 문서**다. 저장소가 아니라 작업 공간(`records/`)에 둔다. 저장소 문서 루트에는 쓰지 않는다.

| 경우 | 저장 경로 |
|---|---|
| 관련 이슈가 있음 | `records/{project}/{task_id}/<파일명>` |
| 관련 이슈가 없음 | `records/{project}/<파일명>` — 이슈를 새로 만들지 말고, 이슈 없이 두었다고 알린다 |

- 문서 저장소(이슈·기록이 있는 clone)의 위치는 `wb --help`의 `문서:` 줄이다. `wb`가 없으면(workbench 플러그인 미설치) 작성하지 말고 사용자에게 알린다
- 경로는 `wb new-record`가 정한다: `--to`에 task_id를 주면 이슈의 `project` 폴더 아래 이슈 폴더에, project 값을 주면 이슈 없는 기록으로 둔다. 이슈가 없으면 문서 저장소의 `projects.tsv`(`wb --help`의 `문서:` 경로)에서 대상 저장소의 `project`를 찾는다
- 그림 등 첨부는 문서와 같은 이름의 폴더에 둔다 (`proposal.md` → `proposal/Fig1-1_현행_플로우.png`)
- 폴더 구조·`project` 값·링크 형식의 정본은 [형식 규칙](${CLAUDE_PLUGIN_ROOT}/references/workbench-format.md)다. 이 스킬과 다르면 그쪽을 따른다

# 작성 규칙

## 프론트매터

```yaml
---
title: 통합 마이페이지 본인확인 방식 검토   # 필수. 본문 H1과 동일
lifecycle: record                           # 필수. 고정값
task_id: CMN-2                         # 이슈가 없으면 생략
repos: [repo-a, repo-b]                     # 필수. 대상 저장소 (없으면 [])
base: main@a1b2c3d                          # 필수. 저장소가 여럿이면 {repo-a: main@a1b2c3d, repo-b: develop@d4e5f6a}
updated: 2026-09-28                         # 필수. 내용이 바뀐 날
---
```

- 새 문서의 프론트매터는 `wb new-record`가 만든다. 위는 형식 참고용이다
- 프론트매터가 없는 기존 기록을 수정하면 **수정하는 김에 추가**한다(`wb new-record … --print`). 알 수 없는 `base`는 `unknown`으로 쓴다

## 링크

- **파일 기준 상대경로**로 쓴다. 이슈 폴더의 문서에서 `../../../../`가 workbench의 상위 폴더(워크스페이스 루트)이고, 저장소는 그 아래 워크스페이스 폴더를 거친다
  - 저장소 문서: `../../../../{워크스페이스 폴더}/{저장소}/{문서 경로}#섹션`
  - 코드: `../../../../{워크스페이스 폴더}/{저장소}/{코드 경로}` + 본문에 라인 번호
  - 같은 이슈의 다른 기록: `design-access-grant.md`
- `file:///D:/...` 같은 절대경로는 쓰지 않는다
- 저장소 문서·코드는 참조할 수 있지만, 그 내용을 옮겨 적지 않는다 (대원칙 4)
- 코드 링크는 `base` 시점 기준이다. 판단의 핵심 근거가 되는 코드는 몇 줄 인용해 두어도 된다(코드가 바뀌어도 판단 근거가 남도록). 인용은 10줄 이내

## 구조

- `<details>` 사용법, mermaid, ASCII 다이어그램 금지는 `/workbench:documentation`의 [계층적 노출](../documentation/SKILL.md#계층적-노출-details)과 [링크와 구조](../documentation/SKILL.md#링크와-구조)의 규칙을 따른다 (단, 링크 경로 형식은 위 [링크](#링크)를 따른다)
- 항목을 다른 문서에서 참조하게 되면 번호를 붙인다 (`R-1` 요구사항, `P-1` 선결 조건, `S1`/`A1` 검토 항목, `O-1` 미결 사항). 삭제해도 번호를 재사용하지 않는다
- 한 문서는 **400줄 이하**를 권장한다. 넘으면 하위 주제로 나누고 상위 문서에서 링크한다
